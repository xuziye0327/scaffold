# Agent Development Guidelines

## Use Bun

- Use Bun as the package manager. Run all commands from the project root, where `package.json` and `bun.lock` are located. Do not introduce another package manager or its lockfile.
- When modifying `package.json`, use Bun commands whenever Bun supports the change. Do not edit this file directly or rewrite it with scripts in those cases.
- Install existing dependencies with `bun install --frozen-lockfile` to preserve the locked dependency graph. If the manifest and lockfile are inconsistent, investigate the cause before regenerating the lockfile.
- Use the appropriate Bun commands to manage dependencies. When adding or migrating third-party dependencies, follow the approval requirements in the next section:

  ```sh
  bun add <dependency>
  bun add --dev <dependency>
  bun remove <dependency>
  ```

- Use `bun pm pkg set` and `bun pm pkg delete` to manage package metadata and scripts. For example:

  ```sh
  bun pm pkg set 'scripts.lint=oxlint'
  bun pm pkg delete 'scripts.<name>'
  ```

- Run project tools through the scripts in `package.json`, such as `bun run fmt:check`, `bun run lint`, and `bun run build`. Use the project's installed tools rather than fetching a different version for the same task.
- Edit `package.json` directly only when Bun does not support the required change. Before editing, explain which change Bun does not support and why. Limit the edit to the necessary fields.
- A failed command, an unavailable network connection, or a missing subcommand does not mean Bun lacks support for the change. None of these conditions permits bypassing this rule.
- Preserve dependency versions, dependency types (`dependencies`, `devDependencies`, `peerDependencies`, and `optionalDependencies`), and registry or Git sources unrelated to the task. Do not perform unrelated dependency updates.
- Let Bun generate and maintain `bun.lock`; never edit it by hand. Review all manifest and lockfile changes produced by Bun to ensure they stay within the authorized scope.

## Dependency Changes

- Obtain user approval before adding or replacing a third-party dependency, or changing its version requirement, dependency type, registry, or Git source. An explicit request naming the dependency and the change counts as approval.
- Keep approval scoped to the requested packages and changes. Do not include unrelated dependency or lockfile updates.
- Remove a dependency only when requested or when the authorized change makes it unused. Ask before removing it for any other reason.
